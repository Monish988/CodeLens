CodeLens Code Health and Heatmaps — full design breakdown covering complexity scoring, churn visualization, and stale code detection with implementation notes

Complexity scoring + hot spot heatmap
Cyclomatic complexity is calculated from the AST — every branch point (if, else, ternary, loop, catch, &&, ||) adds 1 to a function's score. The result maps directly to "how many test cases does this function need." Scores are displayed as a live overlay on the file tree, inside code previews, and as a dedicated Complexity tab per entity.

Inline complexity annotation in code preview additive▶
What
When viewing a file in the code preview panel, function definition lines get a small score chip in the right gutter. Amber/red chips are immediately visible without clicking anything.
Interaction
Clicking a gutter chip opens the Complexity tab for that function in the right panel. No modal, no tooltip — just tab navigation. Keeps the preview readable.
Threshold
Only show chips for score ≥ 6. Functions scoring 1–5 get no annotation — they don't need attention. Showing everything creates noise.
!
Don't annotate every line. Only function declaration lines get chips. Annotating branches inside the function body creates visual clutter and shifts developer focus from code to tooling.
New creative additions — beyond the PRD
Complexity diff on git changes
When churn integration is active, show "+3 complexity" or "-2 complexity" next to a function that was changed in the last commit. Helps developers see if their changes are making things worse.
Team complexity leaderboard
If multiple devs use CodeLens on the same repo: a "Top 10 most complex functions" list in the Health dashboard, with file path, function name, and score. A wall of shame that drives refactoring culture.
Complexity over time chart
Using git log integration: a sparkline showing how a file's complexity score has trended over the last 30 commits. Upward slope = accumulating debt. Shown in the Complexity tab.
"Safe to refactor" confidence badge
If a function has zero dependents (from the Impact system) AND high complexity, badge it "Safe to simplify — no call sites affected." Combines blast-radius + complexity data.
Churn visualization
Churn = how frequently a file changes. Computed from local `git log --follow --format="%ad" -- {filepath}` for each file in the index. High churn + high complexity = your biggest technical debt. The data is overlaid on the existing dependency graph AND the file tree simultaneously.
The churn heatmap calendar
Churn calendar widget inspired by GitHub contributions▶
What
Per-file, a 7×N grid of day cells (last 90 days) where cell darkness = number of commits touching that file that day. Shown in the right panel when a file is selected under the Health tab.
No changes 1–2 commits 3–5 commits 6+ commits
Time range
Segmented control above the calendar: 7d 30d 90d All. Default: 90 days. Changing the range recalculates and re-renders the grid instantly from the cached git log data.
i
Implementation: run `git log --format="%ad" --date=short -- filepath` once per file at index time. Cache the date array in SQLite. The calendar is pure JS rendering from that array — no re-running git for each interaction.
Dual-encoding on the dependency graph most impressive feature▶
Encoding
Node size = complexity score. A function with complexity 14 renders as a large node. A complexity-3 function is small.

Node color intensity = churn. Low churn = dim. High churn = bright red. A large, bright-red node is your #1 tech debt priority.
User flow
Open Dependency Graph→ Toggle "Health overlay"→ Nodes resize + recolor→ Large red nodes jump out immediately→ Click → Impact + Complexity tabs
Tech debt badge
Files in the top 25% of both complexity AND churn simultaneously get a special badge on their graph node: a small red diamond icon. This is the "automatic tech debt detector" — no manual review needed to find the worst files.
Legend
Persistent legend panel (collapsible) at top-right of graph: two scales shown as visual examples — a small dim node vs a large bright node — with labels. Never hidden, since dual encoding without a legend is confusing.
Without overlay
All nodes same size, same color. You can see call relationships but no sense of risk or debt. The graph is informational but not actionable.
With health overlay
One glance reveals the 3–4 files that need attention. The graph becomes a risk map, not just a structure map. Developers know exactly where to start their next refactoring sprint.
!
Node size encoding caveat: Very small nodes become unclickable. Set a minimum render size (e.g. 12px diameter) regardless of complexity score. Nodes below the minimum still show a score tooltip on hover.
Churn spike alerts proactive, not reactive▶
What
If a file is indexed and CodeLens detects it has been changed 3+ times in the last 7 days AND has complexity ≥ 8, show a non-intrusive banner in the status bar: "App.jsx has high churn this week — review recommended."
Design
Status bar entry (bottom of app) with an amber dot. Clicking it navigates to the file's Health tab. Never a modal or toast — alerts that interrupt workflow are ignored. Status bar items are glanceable.
Snooze
Right-click the status bar alert → "Snooze for 7 days." Stores a timestamp in SQLite so the alert doesn't reappear until a week passes or the churn pattern resets.
Creative additions
Commit message preview on hover
Hovering a churn calendar cell shows a tooltip with the commit messages from that day. Context for why the file was churning — "fix: auth race condition" is different from "wip: refactoring".
Author churn attribution
Optionally show which developer accounts for most churn on a file. Color-coded by author initials. Useful for identifying who knows a file best before refactoring.
Churn vs complexity trend line
A small 2-axis sparkline: complexity on Y, churn on X, plotted over time. Files trending toward the top-right corner (high both) are actively getting worse.
Stale code detector — orphan finder
An orphan function is a function definition that exists in the SQLite index but has zero rows in the `calls` table pointing to it. This is a pure database query. The design challenge is making the results trustworthy, actionable, and safe — CodeLens must never delete anything itself.
The orphan finder interface
Orphan results page design pure SQLite — no AI needed▶
Layout
Dedicated sub-page under the Health section (not a panel). Full-width results table with filtering + sorting controls at top. Each row is one orphan function.
Row anatomy
Each row shows: function name (monospace, green) · file path (muted, truncated) · lines of code (the weight of the dead code) · age (days since last git touch) · status actions (Keep / Flag / View).
Sort options
Default: "Largest first" (LOC descending — biggest dead code = highest priority). Also: "Oldest first" (longest untouched), "By file" (group orphans that live together).
Filter bar
Three filter pills: All (47) Flagged (12) Kept (8). Clicking Flagged shows only the functions the user has marked for deletion review.
!
False positive banner — always visible: "Dynamic calls (eval, require, computed property access) are not detected. Verify before deleting." This is non-dismissable. One wrong deletion breaks production — the disclaimer must always be present.
Keep / Flag / Ignore workflow state persisted in SQLite▶
Three states
Unreviewed (default) — no action taken. Flagged — user thinks this can be deleted. Kept — user has confirmed this is needed (e.g. it's called dynamically).
Actions
Two icon buttons per row on hover: checkmark (Keep) and flag (Flag for deletion). These toggle — clicking a second time resets to Unreviewed. State stored in a `orphan_review` table in SQLite.
Visual diff
Flagged rows get a subtle red left-border. Kept rows get a green left-border and reduced opacity (they're resolved — less visual weight). Unreviewed rows look normal.
Bulk actions
Checkbox column on the left. Select multiple → "Flag selected (12)" button appears in toolbar. For users who want to batch-review rather than row-by-row.
i
Session persistence: the keep/flag state should survive app restarts. Store in SQLite with columns: `function_id`, `status` (unreviewed/kept/flagged), `reviewed_at`. Reset status when the file is re-indexed (function changed).
Export and developer handoff critical for team use▶
Export formats
Markdown table — paste into GitHub issue or Notion. JSON — pipe into custom tooling or CI checks. Plain text list — one `filepath:functionname:line` per line, copyable into any text editor.
Export scope
Three options in the export dialog: "All orphans," "Flagged only," "Unreviewed only." Default is "Flagged only" — the ones the developer has decided are deletable.
GitHub issue template
A special export button: "Create GitHub issue draft." Opens the system browser with a pre-filled GitHub new-issue URL. Body contains the Markdown table. Title: "Tech debt: 12 orphan functions identified by CodeLens." Developer just clicks Submit.
✓
This export-to-GitHub pattern is the highest-value feature for teams. It turns a solo tool into a team communication tool without any backend infrastructure. The URL-encoding of the issue body is a single `encodeURIComponent()` call.
Creative additions
LOC savings counter
At the top of the orphan page: "Deleting all flagged functions would remove 847 lines of code." Updates live as the user flags/unflags rows. A motivating number that makes the refactoring feel tangible.
Orphan clustering
If 5+ orphan functions live in the same file, group them under a collapsible file header with a "Review all in file" bulk action. Files with many orphans are candidates for full deletion or major restructuring.
Re-check on demand
A "Re-scan for orphans" button that re-runs the SQLite query against the latest index. Shows "Last scanned: 3 mins ago" so users know if the results are fresh after code changes.
Orphan age heatmap
Color-code orphans by age: green = added recently (might be in-progress), red = untouched for 6+ months (almost certainly dead). Age from git blame on the function's first line.
Unified health score — the codebase dashboard
A single Health Score (0–100) computed from all three signals: complexity, churn, and orphan density. This becomes the homepage of the Health section — a cockpit view that surfaces the most important issues without the developer having to check three separate tabs.
The health dashboard layout
Score computation + display synthesizes all 3 systems▶
Score formula
Health = 100 − (complexity_penalty × 0.4) − (churn_penalty × 0.35) − (orphan_penalty × 0.25). Each penalty is normalized 0–100 based on file counts. Weights are opinionated defaults but configurable in Settings.
Visual design
Large score number center-top of the Health page (e.g. "72") with a color-matched label ("Fair"). Below: three sub-scores with their own chips — Complexity 61 / Churn 80 / Orphans 88. Each sub-score links to its full section.
Score history
A 30-day sparkline below the main score. Shows whether the codebase is getting healthier or worse over time. Computed from SQLite snapshots taken at each re-index.
✓
Implementation: store a `health_snapshots` table with `(snapshot_date, complexity_score, churn_score, orphan_score, total_score)`. Insert one row per full re-index. The sparkline reads from this table.
Priority action list — "fix these 3 things first" most actionable▶
What
Below the score: a ranked list of the top 5 most impactful actions the developer can take right now. Computed by cross-referencing all three signals: high complexity + high churn + many dependents = highest priority.
Row format
Priority number (1–5) · file + function name · reason badge ("High complexity," "High churn," "Orphan cluster," "Tech debt") · estimated LOC impact if fixed · "Review" deeplink button.
Reasoning
Each row has a one-line explanation: "This function has 14 branches, was changed 8 times last month, and has 5 dependents. It's your highest-risk file." Combines data from all three systems into readable prose.
i
The priority ranking algorithm: sort by (complexity_score × churn_factor × dependent_count). This naturally surfaces the files that are complex, frequently changed, and widely used — the exact intersection that defines technical debt risk.
Health report export for team / stakeholders▶
Output
A single-page Markdown report: codebase name, health score, sub-scores, top 5 priority list, orphan count, most complex files table. Ready to paste into a team Notion, Confluence, or GitHub discussion.
Trigger
"Export health report" button at top-right of the Health dashboard. Opens a preview modal, then "Copy as Markdown" or "Save as .md file" via system dialog.
Scheduled reports
Optional: in Settings, enable "Weekly health digest." Every Monday at 9am, CodeLens generates a report and shows a notification badge on the Health nav item. Entirely local — no email, no cloud.
Creative additions — beyond the feature request
Health score as a CI gate (local)
A CLI flag: `codelens --health-check --threshold=70`. Returns exit code 1 if health score is below threshold. Developers can add this to a pre-commit hook or local CI script to prevent merging debt-heavy code.
Before/after score on AI refactors
When the AI Refactor Sprint generates a suggestion, show the projected score change: "Accepting this refactor would raise your Complexity score from 61 → 74." Makes the value of refactoring concrete.
"Code debt budget" setting
In Settings: set a maximum acceptable complexity score (e.g. 10) and a maximum orphan count (e.g. 20). The health dashboard shows a "Budget used: 67%" indicator. Teams can enforce standards without code review.
Workspace comparison
If the user adds a second workspace, show a side-by-side health score comparison. Useful for monorepos, microservices, or comparing a refactored branch against main.
